### 4. 移动端横向溢出——真因不是 `.scene-body`

上一段记的「`.scene-body` 在 640 断点没变单列」是错的。`.scene-body` 在 `@media (max-width: 1024px)` 就已经变单列了。

真因：**`@media (max-width: 860px)` 里 `.law-hero-grid { grid-template-columns: 1fr }`**。`1fr` 的隐式最小值是 `auto`，等于 `minmax(auto, 1fr)`，所以第一列的轨道宽度会被内容的最小内容宽撑开。`reply-all` 那条的 `hero-echo` 是一排 `flex-wrap: nowrap` 的「收到」气泡（最小内容宽 774），直接把整列撑到 594、整页 `scrollWidth` 到 612。所以只有 `/reply-all/` 一页坏，其它 79 页都正常。

修法：改成 `minmax(0, 1fr)`。改完 375px 下 `scrollWidth == clientWidth`。

## bekind：场合筛选（首页第二根轴）

搜索框下面加了一排 chips：**群聊 / 私聊 / 邮件 / 公开平台**。和四个分类不重叠——分类讲主题，场合讲场景，所以它是「往里收」的筛选而不是第二套导航。

### 数据结构

- `src/data/law-types.ts`：导出 `SituationId = 'group' | 'dm' | 'mail' | 'public'` + `situations` 注册表（id/label）。`CategoryId` 仍然不导出。
- `src/data/law-situations.ts`：`Record<slug, SituationId[]>`，按 slug 挂，和 related/caveats 一个套路，不动 laws.ts。
- **判定标准只有一条：换个场合这条还成立吗？** 成立就不标。所以 19 条是空的（别当混蛋、奥卡姆剃刀、沉没成本、各种认知偏差），这是有意的，不是漏了。
- 单条最多挂两个。挂多了就成了万金油，筛出来也没信息量。
- `lawSituationsOf()` 按 situations 表顺序排序输出，避免 DOM 上出现 `group dm` 和 `dm group` 两种写法。

分布：group 25 / dm 20 / mail 14 / public 23，共标 60 条。

### 交互

- 单选，点一下收起、点第二下还原；和搜索是**交集**。
- URL 记 `?s=`，与 `?q=` 并存，刷新/分享都能还原；非法 `?s=zzz` 静默忽略。
- 状态行（找到 N 条 · 清除筛选）移到 chips **同一行的右侧**，不然把它单独放一行时，没筛选状态下会在 chips 和列表之间留一条空的 20px，看着像个洞。
- 分区计数与隐藏逻辑从「有 query 才收」改成「有任一筛选就收」。
- 点 chips 后如果 `#laws` 还在视口下方 60% 以外，才 `scrollIntoView`，避免已经在看列表时被拽一下。

### 踩到的坑

- **`repeat(auto-fill, minmax(292px, 1fr))` 在 320px 屏会溢出**：容器只有 269px，但列最小 292px，硬撑出 10px 横向滚动。改成 `minmax(min(292px, 100%), 1fr)`。同时把 640 断点里的 `.card-grid { grid-template-columns: 1fr }` 改成 `minmax(0, 1fr)`——同上一条 `1fr` 隐式 `auto` 的坑。
- 探针脚本自己写错一次：连点同一个 chip 两次把场合关掉了，却以为「场合 + 查询」失效。看数据前先确认自己的探针逻辑。
